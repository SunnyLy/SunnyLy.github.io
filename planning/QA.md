# Knowledge Base Acceptance Plan

## Scope and evidence

Validate the built site in a browser, using the category configuration as the single source of truth for navigation and links. Record the tested URL, commit or working-tree state, browser, viewport, result, and screenshots for visual or interaction checks. Browser device emulation validates responsive layout; it does not count as physical-phone verification. State physical-device coverage separately.

Use the repository's browser workflow for end-to-end checks against a local production build. A successful build alone is insufficient. Cover a desktop viewport and widths of 320, 390, and 768 CSS pixels, plus a real mobile browser when accessible. Do not create unit tests that merely repeat component markup or library behavior.

## Release-blocking checks (P0)

1. **Navigation and reading:** Every configured category opens a substantive landing page or note. The left navigation highlights the current page; mobile navigation opens, closes, and permits reading without obscuring content. Heading links, browser back/forward, direct article URLs, and direct refresh work. A reader can reach a note without JavaScript-dependent routing being the only source of its content.
2. **Chinese search:** Search finds a distinctive Chinese phrase present only in note body text, not its title. Verify title search, mixed Chinese/English technical terms, an empty query, and a no-result query. Selecting a result opens the correct page and relevant section. Search remains operable with keyboard and mobile touch.
3. **Responsive content:** At every target width, the page itself has no horizontal overflow. Long code, tables, images, and diagrams remain usable through local scrolling or their dedicated viewer. Text is readable at browser zoom of 200%; controls remain reachable. Verify actual rendered dimensions and screenshots rather than relying only on CSS declarations.
4. **Images:** Test Markdown images and raw HTML `img` elements, including a caption, a large portrait image, a broken URL, an image inside a link, and a small image. Opening a large image shows useful detail; dismissal works through its close control and Escape. Focus enters the dialog, stays inside it while open, and returns to the initiating element. Backdrop and close controls work on touch. Linked images retain an explicit, usable destination action. Broken images expose useful alternative text without trapping the reader in an empty viewer.
5. **Mermaid:** A valid flowchart renders after initial load and internal navigation. Its viewer supports zoom in, zoom out, reset-to-fit, pointer/touch drag, and two-finger pinch. Test pinch when the available tools or physical device support multi-touch; otherwise report it as unverified, not optional implementation. Verify full-screen entry and exit, including viewport-filling dialog fallback when the Fullscreen API is unavailable or rejected. Visible zoom buttons remain the touch alternative, and ordinary page scrolling stays usable outside the viewer. Scaling remains bounded and reset restores a visible diagram. An invalid or unsupported diagram displays readable source or a clear error and never leaves indefinite loading or breaks surrounding content.
6. **Lifecycle and accessibility:** Repeat image and diagram interactions after several page changes and light/dark theme switches. Confirm no duplicate viewers, stale diagrams, lingering scroll locks, blocked navigation, or new console errors. Controls have accessible names, visible keyboard focus, and sufficient visual contrast; honor reduced-motion preferences. A failed media item must not disable search or article navigation.
7. **Publishing and preservation:** The production build and GitHub Pages workflow succeed, with the built output used as the published artifact. Verify the root page, an article deep link, a deep-link refresh, local assets, and search assets on the Pages URL when deployment is available. Preview locally before publication; record live checks as pending if publication is outside the authorized scope. Existing dated articles, gallery, Android App Links JSON, and installation page retain their original URLs and required assets. Compare hashes of `.well-known/assetlinks.json`, `tyinstall.html`, and copied legacy resources. Assert the artifact excludes `AGENTS.md`, `planning/`, `.git/`, `CNAME`, dependency folders, and authoring source paths. In isolated temporary fixtures, verify the legacy copier rejects symbolic links and destination collisions without modifying repository source files. No expired-domain redirect or mandatory expired-domain resource is introduced.

## Visual review

Review the homepage and a representative long article in both themes. Check hierarchy, typography, whitespace, active navigation, table of contents, code contrast, empty states, and consistent controls. Mobile screenshots must show real article content as well as the landing page. Check that counts, dates, reading times, and claims reflect available content; do not fabricate activity or popularity.

## Verification sequence

Run documented install/build checks and `git diff --check`, then serve the generated output. Inspect console and failed requests while exercising P0 flows. Use temporary browser fixtures or clearly labeled sample documentation to exercise broken media and invalid Mermaid. Keep fixtures isolated from public production navigation unless they are intentional reader-facing examples. Capture evidence before and after any fix, rerun the affected journey, and repeat build checks only when the fix changes generated output or build configuration.

Release acceptance requires all P0 checks to pass in their available environments. Record untested physical-device or live-deployment checks explicitly; do not describe emulation or local preview as proof of those environments.
